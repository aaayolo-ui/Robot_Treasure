# Robot_Treasure 团队协作与 Git 分支使用说明

本文是 [00_Git使用说明.md](00_Git使用说明.md) 的补充，面向多人同时开发同一项目的情况。重点是：每个人在自己的功能分支上完成一项任务，再通过 Pull Request（PR）合并到稳定的 `main` 分支。

## 1. 分支是什么

Git 分支是代码的独立开发线，不是聊天分组。

- `main`：稳定分支，只保留已经检查或测试过、可以供全组使用的内容。
- 功能分支：为一个具体模块或任务创建的临时开发线，完成并合并后可以删除。
- 一个分支只处理一项任务，分支名使用功能名称，不使用个人姓名。

本项目可使用下列命名方式：

```text
feature/motor-md240a
feature/gray-nchd12
feature/tof-ai1811
feature/encoder-mc520
```

## 2. 开始一项任务

每次开始新任务前，先回到 `main` 并获取团队最新代码，然后创建自己的功能分支。

```powershell
cd F:\Robot_Treasure
git switch main
git pull origin main
git switch -c feature/gray-nchd12
git branch
```

命令说明：

- `cd F:\Robot_Treasure`：进入项目根目录。
- `git switch main`：切换到稳定分支。
- `git pull origin main`：从 GitHub 获取并合并远程 `main` 的最新内容。
- `git switch -c feature/gray-nchd12`：创建并立即切换到灰度模块功能分支。实际使用时请替换为自己的任务名。
- `git branch`：查看本地分支；前面带 `*` 的分支就是当前所在分支。

创建分支前先确认工作区没有与本任务无关的修改。若已有未提交内容，先与负责人确认其归属，不要直接带入新任务。

## 3. 开发与提交流程

完成一个可以检查的小阶段后，使用下面的流程提交到本地仓库：

```powershell
git status
git add .
git status
git commit -m "完成NCHD12灰度模块基础读取"
```

命令说明：

- 第一次 `git status`：查看哪些文件被修改、新增或删除。
- `git add .`：将当前目录下的修改加入暂存区。只有在确认列出的文件都属于本次任务时才使用它；不确定时，改用 `git add 路径\文件名` 精确暂存。
- 第二次 `git status`：确认“准备提交的更改”只包含本次任务内容。
- `git commit -m "..."`：把暂存区内容保存为一条本地提交记录。

提交信息不要写成“修改”“更新”等模糊文字，应说明完成或修正了什么。例如：

```text
完成PCA9555基础读取
完成AI-1811串口数据解析
修正MD240A右后电机方向
补充MC520编码器测试记录
```

建议每完成一个可编译、可检查或可测试的阶段就提交一次。不要把多项无关工作堆到同一条提交中。

## 4. 首次推送功能分支

新建分支第一次推送时执行：

```powershell
git push -u origin feature/gray-nchd12
```

其中 `-u` 用于建立本地分支与远程同名分支的关联。设置后，后续在该分支上完成提交只需执行：

```powershell
git push
```

推送前再次执行 `git status`，确认没有把临时文件、无关资料或其他成员的工作带入本次推送。

## 5. 多人协作注意事项

1. `main` 只保存已检查或测试过的稳定内容。
2. 开始任务前必须从最新 `main` 创建功能分支。
3. 不要直接在 `main` 上开发。
4. 一个分支只处理一项任务。
5. 优先只修改自己负责的模块。
6. 必须修改其他成员模块前，先沟通并说明修改范围。
7. 不要随意删除、移动或批量重命名文件。
8. 商家示例代码只能作为参考；使用前要确认其适用型号和接口，不能直接当作项目正式代码。
9. 每次提交应对应一个可验证阶段，并写清楚提交信息。
10. 每次 `git push` 前都先检查 `git status`。
11. 不提交编译缓存、临时文件、无关大文件、商家安装程序或宣传资料。
12. 发生冲突时先联系负责人确认，不要盲目选择“全部保留”或“全部接受”。

以下文件容易被多人同时修改，发生冲突的风险较高：

```text
*.ioc
main.c
gpio.c
tim.c
usart.c
stm32f1xx_it.c
Keil 工程文件
```

当前团队约定：CubeMX 引脚、定时器、`.ioc` 文件和 Keil 主工程配置由指定集成人员维护。其他成员如需改动这些共享配置，必须提前沟通并由集成人员确认后处理。

## 6. Pull Request 使用方法

Pull Request（PR）是把功能分支申请合并到 `main` 的页面记录。创建 PR 不等于已经合并；它的作用是让负责人和队友查看修改文件、提交记录和测试情况，再决定是否合并。

当前仓库尚未设置 `main` 的强制保护规则，因此更需要依靠团队约定：不要自行合并自己的 PR，必须等待负责人审核和合并。

### 网页创建 PR 的步骤

1. 完成功能分支上的一个可检查阶段。
2. 执行 `git push`，将本地功能分支推送到 GitHub。
3. 在浏览器打开本项目 GitHub 仓库。
4. 点击页面出现的 **Compare & pull request**。
5. 确认 `base` 为 `main`，`compare` 为自己的功能分支。
6. 填写清晰的 PR 标题。
7. 在描述中写明完成内容、修改文件和测试结果。
8. 点击 **Create pull request**。
9. 将 PR 链接或分支名称发给负责人。
10. 等待负责人审核、提出修改意见或合并。

PR 标题示例：

```text
完成NCHD12灰度模块基础读取
完成AI-1811串口数据解析
修正MD240A右后电机方向
```

PR 描述可直接使用下面模板：

```markdown
## 本次完成
- 

## 修改文件
- 

## 测试结果
- Keil编译：
- 实物测试：
- 其他测试：

## 尚未解决
- 

## 注意事项
- 
```

### 负责人合并 PR 的步骤

1. 打开对应 PR。
2. 查看 **Files changed**，确认没有影响其他模块。
3. 查看提交说明和测试结果是否完整、可复核。
4. 有问题时要求提交者在原分支修改后再次推送。
5. 确认无误后点击 **Merge pull request**。
6. 确认合并操作，并通知全组更新 `main`。

其他成员收到通知后执行：

```powershell
git switch main
git pull origin main
```

## 7. 不要这样做

- 不要直接在 `main` 分支开发。
- 不要把未经检查或测试的内容直接推送到 `main`。
- 不要自行合并自己的 PR。
- 不要随意修改 CubeMX 共享配置、`.ioc`、定时器和 Keil 主工程配置。
- 不要在一次提交中混入大量无关修改。
- 不要使用“更新”“修改一下”等模糊提交信息。
- 不要提交商家压缩包、视频、EXE 程序、临时文件或编译产物。
- 不要在冲突发生时不看内容就覆盖其他人的修改。

## 8. 每日协作检查清单

开始开发前：确认当前分支、执行 `git pull origin main` 获取最新稳定代码。

提交前：执行两次 `git status`，确认暂存区只包含本次任务。

推送后：创建 PR，填写测试结果，并等待负责人审核合并。
