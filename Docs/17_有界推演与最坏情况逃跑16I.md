# 16I：有界推演与最坏情况逃跑

2026-10-13。独立工程 `Thief16I_RolloutMinimax_FourLaser_Test`，由16H复制。

**仅编译通过，尚未完成硬件验证**。

这一版将逃跑选择改为“多条路线、多个警方行为假设、整段转移推演”。实际STM32 C代码已经接入应用层，并由Cortex-M3模拟器执行来产生回放。完整比赛中的接触时间延后，但尚未得到持宝到限时的胜局，也存在专项场景退步。

## 算法如何决定路线

1. 离线根据原地图枚举无重复节点的路线，保留不同目标、到达朝向、起步方向，以及前两次拐弯路口不同的备选。每组至多6条，路线至多28个节点、18秒。生成579条只读候选，单个起点/朝向最多67条。现场按已经检测到的来车方向排除起步就迎向目标的候选。
2. 只从本车定位和最新、有效、已确认的激光地图投影建立警方位置假设。不同通道同时报告互相矛盾的位置时，不强行当成一个确定位置，转用原16H后备搜索。没有输入回放中警方的真实全局坐标或隐藏路线。
3. 对每条候选推演六种警方行为：两种参考速度，分别配合沿最后轨迹追踪、另一方向局部搜索、按最后可见运动方向提前拦截。速度参考为674和815mm/s，后退按参考速度比例换算；警方转向768ms是模型假设，尚未测得对手的最短转向时间。
4. 推演从当前藏点覆盖到下一个藏点，并继续覆盖340ms准备窗口。按行驶、转向和换向的阶段结束事件推进，检查整个相对运动区间的激光可见性及车身扫掠接触。候选最长18秒，窗口上限20秒，正常候选均可完整检查，不把6秒以后直接视为安全。
5. 全部六种假设都能完成转移的路线优先。若全部候选都有风险，把各模型的接触时刻从早到晚排序，先最大化最早接触时刻，再比较第二早、第三早时刻，即maximin/leximin。只有推演完成的路线才比较下次脱身余量、藏点曝光、距离和时间；发生预测接触后，不再假装已经到达目标去计算收益。
6. 优先计算最快拦截假设。未算的模型暂按最乐观的“完成转移”处理；即使如此也比当前最好方案差，就剪去该候选的剩余计算。这是分支限界，不是随意缩小搜索数量。36组输入的剪枝前后决策全部相同。

这是有限候选、有限警方模型的鲁棒启发式选择，不是完整对抗博弈树，不具备全局最优或必胜证明。警方时间查表按815mm/s生成；较慢假设借此选择路线，属于启发式，未分别存放每种速度的精确最短时间表。

## 如何使用“刚才这条路没有车”

连续四帧高质量远距回波后，如果终止直道的T口首次出现目标，可以结合地图推测它从侧路进入。程序保留首次出现时刻，扣除已经过去的时间后，推演参考转向的剩余耗时。

零距离、低置信度、断帧不能当成空路；线索有时间限制，换藏点后重置。这个判断仍依赖可靠测距、准确定位和对手运动模型。相关漏检或对手已经提前转好方向，会使推断失效；它不能证明目标身份或真实车头方向。

同一算法仅关闭入口推断的开发对照，种子7在同速、警方快10%、快20%下分别于26.73、25.38、24.29秒接触。收益对这一观测模型敏感，不能将仿真增益直接视为实车增益。

## 路线、运动和抓捕约束

- 开局沿用户指定取宝前缀：N054→N053→N044→N036→N035→N034→N033→N025→N015→N006→宝藏区域。地图中的N005宝藏点在N006到N004的直行段上，不停车取宝。
- 初始藏点仍为N038。候选藏点仍为N011、N012、N038、N062，停车轴前后均有直接到下一分岔的活路。先到藏点等待，检测后转移，再藏好等待。
- 起步只能沿当前车头方向前进或后退，不要求底层控制器执行尚未验证的静止原地90度调整。后退不把车身朝向翻转180度。
- 车速、转向、换向参数及0.6米两格检测保持对照一致。规划采用190×198mm车体，以及转向时半径138mm的保守外包方框；实际抓捕仍由16F的连续旋转矩形首次接触判定。预测风险不是裁判提前判负，也没有无敌时间。
- 行驶时激光接收仍沿用基线关闭方案，停车并确认停稳后才检测。因此本版仍可能撞到途中未检测到的车辆。
- 找线位移、惯性、加速度、轮胎打滑、定位误差及激光从安装面到车体中心的距离尚未实测标定。回放仍是运动学近似。

## 相同条件下的结果

完整比赛采用种子10、11、12，同一警方策略、两格传感器、车体及连续碰撞判据。表中为平均首次接触时间。

| 条件 | 16H | 16I | 16I持宝到限时 |
| --- | ---: | ---: | ---: |
| 双方同速 | 35.57秒 | 100.36秒 | 0/3 |
| 警方快10% | 34.20秒 | 95.79秒 | 0/3 |
| 警方快20% | 33.19秒 | 67.32秒 | 0/3 |

另保留七个可直接播放的种子7场景。完整同速场为91.62秒、警方快20%场为67.32秒；它们不是上表三个种子的均值。

必须保留的退步：N038横向等待、上方两格初始已经有警方的同速专项，16H约91.30秒，16I约13.55秒。这反映有限模型的最坏情况目标并不等于每一种真实警方行为下表现最好。N038同轴近距追击等不利场景仍很快被抓，未改变碰撞判据掩盖问题。

## STM32资源和验证

目标为STM32F103RC，沿用原引脚、底层驱动、PID及运动控制。117个Hardware/Control/Core/Drivers/System文件与16H字节一致。

- Keil ARMCC5全量编译：`0 Error(s), 0 Warning(s)`。
- Code 44,792、RO-data 147,084、RW-data 336、ZI-data 35,984字节。Code+RO-data为191,876字节，RW+ZI为36,320字节，落在256KB Flash、48KB RAM容量内。只读推演表138,860字节；算法申报静态工作区15,218字节，非整机RAM或峰值栈统计。
- 实际C算法11,397项检查、UART435项检查均0失败；连续车体/运动模型18项测试通过。
- 579条候选的7,631条连接逐条检查，重生成编号、路径和表数据一致。修改相关速度/时间参数而未重生成表时会触发编译错误。
- 剪枝与不剪枝36组输入的路线、朝向及风险结果相同。实际完整Keil二进制的两个测试输入分别执行约118万和313万条ARM指令；这是CPU模拟器指令统计，不是板上周期或耗时。
- 原100ms规划预算保护保留。真实板上必须检查`PLAN_V3 ... COMPUTE_MS=`；超时会报告`PLANNING_BUDGET_EXCEEDED`并停车。离线结果不能证明所有输入都在100ms内完成。
- 七场回放无更早的未判重叠、无规划故障；18场完整对照无规划故障。88个节点、106条路段及导出JSON保持一致。离线页面事件检查通过；浏览器实际布局与点击、实车传感器/定位/运动未验证。
