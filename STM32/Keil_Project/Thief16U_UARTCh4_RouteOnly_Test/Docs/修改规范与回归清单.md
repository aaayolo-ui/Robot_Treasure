## 每次修改的执行顺序

1. 确认准确工程路径、读取本规范与README、检查Git状态（无Git元数据就如实记录）、核对当前FW标识和源码。备份将修改的文件、原AXF、原日志及源文件散列。
2. 从日志确定触发状态、时刻、原始灰度、YAW、里程及最后故障。区分缓冲回放与当前动作，不能把故障后输出的旧TW记录当作仍在驱动。
3. 为新问题先写最小复现用例，验证原版确实在该断言失败。保存失败记录与复现脚本，不能把无效路线、错误长度或测试装置错误算成原固件缺陷。
4. 只修相关状态机/控制模块。控制算法放Control/Algorithm，应用只调度，main.c和底层硬件不扩散业务。不得用删除全部故障处理、伪造灰度、伪造节点位置来使测试通过。
5. ARMCC5全量编译，并运行新用例及受影响旧回归。模拟车辆模型必须对新增旋转/制动命令作出相应输入反馈；模型也不能直接把目标姿态强行写成已确认状态。
6. 核对每份结果的AXF、源码、测试脚本及依赖脚本SHA-256；改变固件后旧的应用结果必须重跑。纯算法未改动时可保留源码散列相符的独立算法结果。
7. 更新README、增量差异、验证报告和本清单状态。明确区分编译、离线、实车验证；由用户决定烧录与实车运行。
