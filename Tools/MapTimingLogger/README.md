## 接线选择

按项目引脚占用表和基线源码，复用 USART3 调试输出即可。新工程已配置 115200、8N1，无需增加串口或更换引脚。

首次使用建议断电后，先断开车载 USB 转 TTL 与 PB10/PB11 的信号线，按模块实际丝印连接：

| 车载端 | 蓝牙模块端 | 作用 |
| --- | --- | --- |
| PB10 / USART3_TX | RXD | 上传日志 |
| GND | GND | 共地 |
| 用户确认的 5 V 电源 | VCC | 模块供电 |
| 不连接 | TXD | 本次只上传，不需要回传 |

PB11 不接蓝牙。KEY/EN、STATE 等辅助脚本次不使用；表格按引脚名称列出，不代表实体排针顺序。5 V 是用户确认的模块供电值，不等于 UART 信号电平；不能把电源线接到 RXD/TXD。

如果需要保留有线调试，也可在两个 RXD 均为与 STM32 兼容的 UART 输入时，让 **PB10 同时接 USB 转 TTL 的 RXD 和车载蓝牙的 RXD**，由一个发送端向两个接收端输出。PB11 仍只接原 USB 转 TTL 的 TXD，蓝牙 TXD 留空；不得把两块模块的 TXD 同时并到 PB11。共地，不把 USB 转 TTL 的供电输出与车载 5 V 电源并接。首次通信建议先按上表使用单一接收端，确认后再增加分支。

USART1 的 PA9/PA10 被编码器和电机方向占用，重映射 PB6/PB7 被 TFT 占用；USART2 的 PA2 是电机 PWM、PA3 计划用于红外；UART4 的 PC10/PC11 用于编码器；UART5 的 PC12/PD2 用于 JY61P。USART3 的 PC10/PC11 重映射也有编码器冲突。因此本次不增加新串口，也不调整引脚配置。复用功能核对依据为 [ST 数据手册的引脚定义表](https://www.st.com/resource/en/datasheet/stm32f103re.pdf)及 `Docs/07_硬件接线与接口/02_STM32引脚占用总表.md`；实际 MCU 为项目记录的兼容器件，实体排针仍应以开发板为准。

模块型号未知，因此不推断 AT 命令、主从配置或排针次序。已有配对及透传按用户反馈记录，首次采集仍需确认日志清晰、无 CRC 错误或丢序号；不因为能透传就认定计量数据完整。

## 旧分批工程：按已知地图自动运行并记录

`map_routes.json` 和 `map_routes.md` 列出 21 条前进路线，规划覆盖 106 条地图路段的两个方向，共 212 个方向项。新工程 ROM 表含 88 个节点、106 条路段、路线步骤及地图版本签名；每次到路口按路线表选择直行、左转、右转或停车，取消原控制器的固定右转优先。

旧分批工程不包含倒车，按多条路线测全图，每条结束后需要重新摆车。现在新增的连续工程使用用户指定的倒车代码，按文首链接一次启动全图；不要把下述 21 条操作用于新工程。

1. 打开 `map_routes.md`，查看所选 R 编号的起点、格坐标和车头朝向。默认 R001 从 N081（警方出生点）朝地图上方出发。
2. 停止状态：长按 KEY2 或短按 WK_UP 选下一条，短按 KEY1 选上一条。串口输出 `MAP_READY` 确认当前选择。
3. 用户确认摆放及接线后，先启动电脑记录，再短按 KEY2 开始该路线。不要在软件准备阶段自动驱动车辆。
4. 运行中 KEY1/WK_UP 或短按 KEY2 停车；松开这次停车按键后仍保持停止和当前路线，下一次独立按键操作才生效。正常到达路线末端输出 `MAP_ROUTE_DONE`，END 参数为 3；按键中断参数为 1，故障参数为 2。
5. 等 END 及排队记录全部传完，再结束采集。全部路线可分成多个日志文件，重复测量同一路线时也保留各批次。

定位采用已知起点、前灰度路口序列、路线朝向和编码器距离合理性检查；它维护的是路线位置估计，未实现任意位置自动重定位。约 65 mm 轮径来自硬件清单、1560 count/rev 来自原工程，仍是名义里程尺度。传感器漏检可能导致错位；距离异常、缺失所需分支、找线失败或转后航向未在约 90°附近稳定时制动停车，不继续盲走。完整识别效果需要实车验证。

当前沿用基线目标 100 RPM、50 ms 控制周期和转向 PWM=500，启动日志 `MAP_PARAMS` 显示这些参数。所得模型对应这套实际运行参数；更换目标速度、PID、电池条件或轮胎后应分批重新采集，不把不同条件的样本混成一个速度。首次先核对 R001 的第一个路口和右转，完成后由用户正常停车，再延长测试。

N005 是直道上的宝藏标记，其两侧 S 路段合为一次连续直道测量；报告注明共用测量区间，不伪造 N005 灰度事件，也不声称两个 S 的耗时分别被独立测到。

## 旧 MT1 工程的分析方式

Python 分析仅使用标准库：

```powershell
python F:\Robot_Treasure\Tools\MapTimingLogger\analyze.py 日志文件.log --output F:\Robot_Treasure\Tools\MapTimingLogger\results\测量报告.json
```

报告保留每条记录的源时间、序号、编码器累计值、航向角及数据新鲜度，并计算各路口的受控接近、制动等待、旋转、出弯找线和整个流程耗时。时间来自 MCU 的毫秒计数，包含检测和控制调度误差。

完整流程的结束点是连续三次前灰度有效的控制样本（`LINE_STABLE`）；这是软件判据，不能替代实际车姿和线路对齐验证。航向角变化接近 90°的检查单独给出，不把它当作高精度角度校准。

原控制器先旋转约 50°再向前找线。工具按实际角度计算旋转阶段平均角速度，不能用 90°除以这个旋转阶段时间。整个流程时间不能直接当作仿真额外转弯代价，否则可能与直道路段的平移时间重复计算。

序号丢失、CRC 错误、源时钟异常、记录队列溢出、异常停车或缺少首尾记录，会让该批次失效；相关速度不输出。传感器恢复和灰度备用转弯单独标记。运行结束使用车上的正常停止按键；记录程序应继续接收至最后的 END 行及排队记录传完，再结束采集。

```powershell

```

同一路段不同方向和不同进入状态应分别填条目。允许一条测量区间跨多个连续路段，但得到的是这整个区间的平均速度，不能称为其中每条路的独立测量值。`measured_interval_m` 必须是两个时间事件对应物理边界之间的距离，不是自动填入整条路的名义长度。

`map_calibration.template.json` 列出 106 条道路的名义长度及两端节点供核对。已再次读取用户提供的规则 `.doc`：场地 3.6×3 m，相邻黑线中心距 0.3 m，寻迹黑线宽 25 mm。现有地图长度与这个名义格距一致，仍未实地标定；规则中心距不能直接代替传感器事件之间的实际测量距离。宝藏点和普通细分点可能没有灰度检测特征；不能假定每条标注路段的两端都有可直接计时的硬件事件。未确认距离和对应关系时，只提供时间和名义地图参考，不输出“实测车速”。

倒车未完成时，将全图拆成多次前进测试；死路可停车后由用户手动重新放置。原始数据不完整、没测到的道路和没有物理边界支持的区间不能填入估算值冒充标定。

## 旧 MT1 数据协议

ASCII 行格式：

```text
MT1,run,seq,source_ms,event,junction,arg,yaw_x100,yaw_valid,yaw_age_ms,yaw_frames,enc_A,enc_B,enc_C,enc_D,lost*CRC16
```

CRC 为 CCITT-FALSE，初值 FFFF，多项式 1021，覆盖星号之前的 ASCII。`run` 是单次上电中的运行编号，重启后允许重复；分析工具为重复编号生成独立测试批次。`arg` 按事件表示左右转（-1/+1）、正常按键停止（1）、异常停止（2）等。编码器累计计数沿用既有控制更新，可能滞后一个控制周期，不视为瞬时里程。

本轮 15 项电脑端测试通过：源时间/接收延迟隔离、校验错误、丢序号、队列溢出、回绕、重启、缺少结束、误配路段、未标定距离不输出实测值，以及 50°旋转/90°总角度区分。串口采集仅语法检查，未进行蓝牙链路或实车测量。

新 MapRoute 工程采用 MT2：

```text
MT2,run,seq,source_ms,event,junction,route,step,from_node,to_node,arg,yaw_x100,yaw_valid,yaw_age_ms,yaw_frames,enc_A,enc_B,enc_C,enc_D,lost*CRC16
```

数字节点字段在分析时恢复为 N001 等稳定编号；S 路段从同版路线表中直接取出。START 的 arg 是地图/路线签名，不能混用不同版本的日志和表。新增事件 15=NODE_ARRIVE、16=LEG_BEGIN、17=PASS_BEGIN；其余事件与旧 MT1 对应。

当前验证：31 项记录工具测试、107 项策略仿真测试通过；新 MapRoute 工程最终 ARMCC 全量编译为 0 错误、0 警告。另用合成数据核对 21 条路线、212 个方向项的分析及仿真入口，没有将它们当作实车结果。完整文件清单在新工程 `delivery_manifest.json`。**仅编译通过，尚未完成硬件验证**。

完整方案见 `Docs/09_蓝牙路段与转弯标定方案.md`。实际精度必须通过距离复测、独立视频及重复运行确认，不能从数字位数或一次编译结果承诺。

HEX=...` 使旧解析线程异常退出；现已跳过该调试行，并让其他 HEX 负载按字节安全解析。若网页显示“已连接”但接收时间不再推进，应先查服务的 `logs/laser_live_server.stderr.log`；不能把端口已打开当作持续收到数据。

### 地图实时轨迹

同一页面增加了道路地图和橙色行驶轨迹。运行 `Thief16B_UARTCh4_MapStrategy_Test` 时，服务端验证 `MT3` 的 CRC 与地图签名，再利用日志中的起止节点和四轮编码器计数，在对应路段上估计车位；停车后的有效 `LOC` 坐标可更新停靠位置。地图取自本目录 `full_map_route.json`，节点/路段编号与当前运行工程的签名 `436811109` 对应。页面可显示 N001 等节点编号，也可清除当前视图的轨迹。

按开发板 RESET 后，固件重新发出 `MAP_READY`。网页收到且地图签名匹配时，自动清除上次轨迹并把车标放回该路线报告的起点与朝向；当前小偷路线为 N054、朝 N053。这个标记表示**固件预期起点**，按 RESET 并不能证明实车已经被摆回该点。每次实跑前仍需人工摆正小车。无需重新烧录 STM32，更新网页服务并刷新页面即可使用。

地图标题旁的“回到初始位置”按钮也可手动清轨并恢复车标：优先使用最近一次有效 `MAP_READY` 报告的起点和朝向，尚未收到该记录时使用当前小偷工程的 N054、朝 N053。页面标明“手动回到起点 · 待实车摆放”，保留串口连接、四路测距、车载故障状态及原始日志。旧停车位置和普通采样不会覆盖手动起点；收到新的启动、新路段或 `MAP_READY` 后恢复实时定位。按钮只更新网页位置，不向 STM32 发送复位或行驶指令。

四路传感器置信度以 10 格能量条显示，原始百分数仍保留。地图上的“角色”可选小偷（橙色）或警察（蓝色），只改变当前串口轨迹和车标的显示，不会切换车载策略。轨迹以约 30 mm 的道路小段统计经过次数：同方向连续采样只算一次；再次走过同一小段时颜色加深，第 3 次及以上使用最深色。斜向定位修正线保留原色，不参与重复计数。

仅有静止诊断固件的 `CH4_RAW HEX=` 四路数据时，页面会显示激光距离和“等待定位串口数据”，不会根据障碍物距离猜测地图坐标。运行工程的 `LASER DIR=` 日志也可在停车阶段更新四路读数；该工程行驶期间没有连续输出四路激光详情，届时距离卡片会提示超时，地图仍通过 `MT3` 更新。路径是基于编码器和名义地图长度的估计，现场距离尚未实地标定；串口丢帧、轮胎打滑和节点识别偏差会影响显示。新网页尚未在实车行驶中验证。

### 路段内时间预测、灰度板与陀螺仪

地图车标在相邻记录之间可沿当前已知路段预测移动，用虚线和估计范围圆区分于串口轨迹。速度以仿真的名义距离测量值为初值（前进约 0.674 m/s、倒车约 0.679 m/s），再利用同一路段连续编码器样本及路口到达的 **STM32 时间差** 更新；不会把蓝牙接收间隔当作行驶耗时。实际使用值可在“定位详情与使用说明”查看，地图尺寸和速度均未实地标定。

预测最多延伸 700 ms，限制在当前道路中，并在未确认路口前留出余量。收到灰度 `NODE_ARRIVE` 后吸附端点，直到新的 `LEG_BEGIN` 才进入下一段。转向、制动、换向、停车、丢帧与超时会暂停预测；丢帧后需连续采样恢复。相对排队延迟使用 MCU 时钟和接收时钟的最小偏移估计，首次接入前已有的固定链路延迟无法独立测出。预测点不写入实际记录轨迹或重复经过次数。RESET 会清除这些预测状态。

车体前后各显示一块 12 路灰度板，亮格表示处理后识别到黑线。现有固件只在 `NODE_ARRIVE` 提供行进侧灰度：前进更新前板、倒车更新后板；页面注明采样节点、时间和十六进制掩码。没有采样时显示等待，超过 1.5 秒变暗；不会将停车后集中输出的历史 `TW_PIN` 记录当作当前灰度。前板按 P12→P1、后板按 P1→P12 显示。它不是两块灰度板的连续实时采集。

陀螺仪区显示 `MT3` 中的偏航角（原始 `yaw_x100 / 100`）、有效状态、数据龄及接收时间；超过 1.5 秒的旧数据变暗。该角度是传感器自身参考系的读数，不等同于地图正北角。航向误差来自停车 `LOC` 诊断，标为“停靠更新”，无记录时留空；其有效性和年龄另行检查。现有串口未上报俯仰角、横滚角和角速度，因此没有添加这些字段。RESET 同时清空灰度、陀螺仪与停车诊断，避免沿用上一次的数据。
